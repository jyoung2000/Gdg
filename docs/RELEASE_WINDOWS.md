# Releasing Meridian for Windows

## How a release happens

Push a tag.

```bash
git tag v1.0.0
git push origin v1.0.0
```

`.github/workflows/windows-desktop.yml` runs on a Windows runner and does the
whole thing. There is no manual build step and no artefact anyone uploads by
hand — a release is exactly what that workflow produced, which is the only way
the checks below mean anything.

## What the workflow proves before it publishes

Every one of these is a step that fails the build, not a note in a report:

| | |
| --- | --- |
| The Node on the runner is the pinned one | ABI mismatch is the failure mode nobody diagnoses |
| `better-sqlite3` loads | not "the file exists" — it is `require`d |
| Typecheck, then the platform suites, on Windows | paths, shells, process lifecycle |
| The bundled runtime is verified by SHA-256 | a swapped artefact fails here |
| The payload boots on its own runtime | outside the checkout, database created, web client served, stops on request |
| `cargo test --release` | the shell's own logic |
| The installer installs silently | `/S`, `currentUser`, no elevation |
| The installation carries runtime, gateway, web client and migrations | and the installed `node.exe` reports the pinned version |
| Launching it starts a gateway that answers | `/api/system/health` is 200 and `/` serves the client |
| The database and `master.key` exist afterwards | in `%APPDATA%`, created by the bundled addon |
| Killing the shell kills the gateway | an orphan holding the port is a process a user cannot find to stop |
| Reinstalling leaves the database **byte-identical** | hashed before and after |
| Uninstalling removes the program and **keeps** the data | both halves are failures |
| The portable archive unpacks and boots | the same verifier, against the unpacked folder |

The last two are the ones worth being loud about. "Upgrade destroyed the user's
database" and "uninstall deleted the user's work" are the failures people do not
forgive, and neither is visible in code review.

## What gets published

| File | |
| --- | --- |
| `Meridian-Setup-x64.exe` | the installer |
| `Meridian-Portable-x64.zip` | the same application in a folder |
| `SHA256SUMS.txt` | digests of both |
| `SIGNING.txt` | whether this build is signed, read from the artefact |

`SIGNING.txt` is generated by `Get-AuthenticodeSignature` on the file that was
actually built. It is not derived from whether a secret was configured, because
a configured secret proves nothing about an artefact.

## Code signing

The hook is implemented and wired in. **This repository holds no certificate and
invents none.** Until one is configured, tagged builds produce an unsigned
installer, the release says so, and Windows SmartScreen warns on first run —
which is an accurate warning, and better than any of the alternatives.

### Configuring it

`scripts/sign-windows.mjs` runs as `bundle.windows.signCommand` on every
artefact. Two routes:

**A certificate already in the signer's store** — the better one, because no
secret leaves the machine:

```
MERIDIAN_WINDOWS_SIGN_THUMBPRINT = <40 hex characters>
```

Works with a hardware token or an HSM-backed certificate, where the private key
cannot be exported at all. This is where EV and, since 2023, all publicly
trusted OV code-signing certificates live.

**A PFX, as a CI secret:**

| Secret | |
| --- | --- |
| `MERIDIAN_WINDOWS_SIGN_PFX_BASE64` | `base64 -w0 certificate.pfx` |
| `MERIDIAN_WINDOWS_SIGN_PFX_PASSWORD` | its password |

Then set the repository variable `MERIDIAN_REQUIRE_SIGNING` to `1`, and a build
that cannot sign fails instead of quietly shipping an unsigned installer.

Optionally, `MERIDIAN_WINDOWS_SIGN_TIMESTAMP` — an RFC-3161 timestamp server.
It defaults to DigiCert's. Timestamping is what keeps signatures valid after the
certificate expires; without it every release you have ever shipped stops
validating on the certificate's expiry date.

### How the password is handled

It is never an argument. Command lines on Windows are readable by any process on
the machine through WMI, so `signtool /p <password>` hands the password to
anything that is looking — including, on a shared runner, anything anyone else
is running.

Instead the script imports the PFX through PowerShell, which reads the password
from this process's environment; signs against the imported certificate's
thumbprint; and in a `finally` block removes the certificate from the store and
deletes the temporary PFX, which was written owner-only with an explicit ACL.

### Verifying by hand

```powershell
signtool verify /pa /v .\Meridian-Setup-x64.exe
Get-AuthenticodeSignature .\Meridian-Setup-x64.exe | Format-List
```

### SmartScreen

A new certificate has no reputation, so SmartScreen may warn for a while even on
a correctly signed installer. Reputation accrues with downloads. An EV
certificate starts with it. Neither is something to work around, and Meridian
does not try to.

## Before you tag

- [ ] `version` in `package.json` and in `apps/desktop/src-tauri/tauri.conf.json`
      agree, and match the tag
- [ ] `apps/desktop/runtime.json` pins a Node with a current security release —
      if you change it, change `NODE_VERSION` in `.github/workflows/ci.yml` too
- [ ] `pnpm test` is green on Linux, and the Windows workflow is green on the
      commit you are about to tag (run it with **workflow_dispatch** — do not
      find out on the tag)
- [ ] `THIRD_PARTY_NOTICES.md` still describes what is actually redistributed
- [ ] `pnpm licenses list --prod` shows nothing but MIT, ISC, BSD and
      Apache-2.0 — a copyleft dependency compiled into the shipped bundles
      is a licensing decision, not a dependency update

## Updating the bundled Node

Every desktop release ships a Node runtime, so a Node security release is a
Meridian release.

1. Take the version and its SHA-256 from `https://nodejs.org/dist/vX/SHASUMS256.txt`.
2. Update `version`, `abi` and every `artifacts.*.sha256` in
   `apps/desktop/runtime.json`. Digests for all three platforms, not just the
   one you are building.
3. Update `NODE_VERSION` in `.github/workflows/ci.yml`. CI checks that the two
   agree and fails if they do not.
4. **Staying inside the same major matters.** `better-sqlite3` is a native addon
   and Node 22 is ABI 127; a major bump needs a matching addon and a full
   re-verification, not a version string edit.

## If a release goes wrong

Delete the release and the tag. Do not overwrite the assets in place: someone
has already recorded the digest of what they downloaded, and a file that changes
underneath a published checksum is worse than no checksum. Tag `v1.0.1` and let
the record show what happened.
